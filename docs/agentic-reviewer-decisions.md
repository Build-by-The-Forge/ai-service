# Agentic foundation: decisions the reviewer must take

Each item names what is built, what is open, and a recommendation. None blocks the PRs in this series; D4, D5, D8, D9 and D16 block exposure in Release 2. Section 11 of `docs/agentic-architecture.md` lists every difference from the draft specs.

| # | Decision | Built | Recommendation |
|---|---|---|---|
| D1 | **Two tool planes.** `app/core/tools` (three tools, `ToolDefinition`) and `app/core/agentic` (contracts, registry, eight tools) coexist. | The new plane is the only one agentic runs use. The old executor and `AgentExecutor` are untouched. | Keep both until R2 exposure; then retire the old built-ins (`draft.question` is a fixed template) or re-register them as contracts. |
| D2 | **Side-effect taxonomy.** Briefed `read`, `propose`, `write_through_backend` versus existing `READ_ONLY`, `ANALYTICAL`, `PROPOSAL`, `MUTATING`. | New enum; `ANALYTICAL` maps to `read`; write class refused unless the registry is configured for it. | Approve the mapping. Keep write-through-backend off in ai-service; add it only with a backend operation and its own review. |
| D3 | **Permission names.** Draft proposes `progress:read`, `progress:propose`, `plan:read`, `plan:propose`; PRD section 24 names READ, WRITE, SENSITIVE_WRITE, ADMIN, ACADEMIC_REVIEW, OWNER. | The four draft names, plus the existing `content:read` and `assessment:generate`. | Decide how the backend maps them to the PRD categories (a proposal is a WRITE-class request that the backend applies). Names are cheap to change now. |
| D4 | **Gateway capability for agent calls.** Only `chat`, `explain`, `generate_questions`, `cbt_exam` have budgets. | Adapters take a capability string and use `chat`. | Add an `agent` capability with its own per-request budget (calls, tokens, cost) before any real model runs. |
| D5 | **Token accounting.** `ModelCaller` reports no usage. | Tokens are estimated (4 characters per token); the gateway still enforces the real budget. | Either extend the caller to return usage, or give the runtime an `AgentModel` over `ModelGateway.generate`, which has `ModelUsage`. Needed for the signed per-run budget (entitlement design section 6). |
| D6 | **Grade and mastery rule.** The check is a text scan for figures presented as scores. | Floor under the structural rule that no tool lets a model set a score. | Move to a structured final answer (text plus typed claims) when a real model is evaluated; keep the scan as a backstop. |
| D7 | **What progress can be proposed.** Evidence refs must be supplied practice attempts, so a read or review item cannot be marked done on its own. | Three change kinds: `plan_item_done`, `topic_reviewed`, `practice_taken`. | Decide the kinds and their evidence (a reading event? a student confirmation?) with the backend (draft open decision 6). |
| D8 | **Backend contracts.** Assessment-history inputs, the progress-proposal operation and its signed client do not exist. | `SuppliedData` in the signed request (topics, practice evidence, plan, dates) and a `BackendPort` with an in-memory fake. | Adopt `SuppliedData` as the draft for the request contract, written in both repositories; build the signed-client adapter only then. |
| D9 | **Checkpoint, result and idempotency stores.** Only in-memory ones exist; they hold tool arguments, results and answers (student text). | Protocols; reference in-memory versions. | Decide the store (server: Redis or Postgres; device: local database), retention, tenant and user deletion, and encryption before any durable store ships. The idempotency store must be durable, or the backend's key dedupe is the only protection after a restart. |
| D10 | **Resume.** Only interrupted `running` runs resume; cancelled, timed-out, budget and loop ends are terminal. | `resume(task)` returns a finished run's result with no calls. | Confirm. Decide who triggers a resume (the backend re-submitting the signed task is the obvious owner). |
| D11 | **Deadline clock.** The task carries a wall-clock epoch. | Converted to a monotonic deadline at run start. | Server: fine. Device: use the lease's monotonic clock; the epoch only shortens (offline contract section 5). |
| D12 | **Audit trail.** The draft expects the `AgentEvent` stream; this code writes `ToolAuditRecord` per call and checkpoint call records. | An `AuditSink` Protocol with an in-memory sink. | Decide the sink (log, table, backend) and whether to emit `AgentEvent`s from the observer. Records hold ids, digests and codes only; keep it so. |
| D13 | **External MCP tools.** The adapter exists; nothing registers an external tool. | Policy-gated, read or propose only, untrusted output, never evidence, no real transport. | Keep disabled in R2 unless a concrete tool needs it; review a transport (process, network, credentials) separately. |
| D14 | **Evaluation bars and a real model run.** Only a baseline exists; the suite is small and synthetic. | 24 tasks, scripted reference and three negative controls, replayable traces. | Set no bar yet. Next: a real-material set, adversarial prompt-injection tasks against a real model, and a budgeted run through a reviewed script once providers are approved. |
| D15 | **Default limits.** Steps 8, iterations 6, doom-loop 3, no-progress 3, consecutive failures 2, step timeout 30 s. | Per-task fields with these defaults. | Draft suggests 6 steps, 8 calls, 45 s for the planner; set from measurement. |
| D16 | **Exam mode mid-run.** The flag is a snapshot from the signed request. The runtime refuses at start and on resume. | A run already going is not stopped by an attempt that begins later. | The backend must cancel the run (`RunControl.cancel("parent")`) when an official attempt starts. Needs a cancel path in the future route. |
| D17 | **PR stacking.** PRs 2 to 6 are cumulative branches off the previous one, each targeting `main`. | Review the commits after the previous PR's head; merge in order. | Merge 1, then 2, and so on; later PRs then shrink to their own diffs. |
| D18 | **Traces are student data.** A real run's trace holds model answers and tool arguments. | Suite traces are synthetic. | Treat real traces as student data: retention, deletion, no export outside the tenant. |
